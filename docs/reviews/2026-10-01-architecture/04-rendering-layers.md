# Rendering, picking and preview/export boundaries

Reviewed baseline `59bc72668a33fba550c7d8ba14b8bb3ab28abe2a`, against the current architecture, navigation, selection, solids and decorator contracts. This is a review proposal, not a change to those contracts. Source observations below are static unless explicitly identified as a probe. No full tests, native geometry checks, browser acceptance or GPU profiling ran in this lane.

## 1. P1: Preview delivery and worker memoization disagree about completion

`PreviewQueue.submit` increments its epoch when a newer settled document arrives during an active request (`src/decorators/preview-queue.ts:55–59`). Unlike a source change, this does not terminate the retained worker. `pump` subsequently drops the entire old response when its epoch differs (`:87–95`). Meanwhile, the worker records a successfully generated instance as rendered before posting it (`src/decorators/preview-worker.ts:118,136,159`), and `needsRender` skips instances with unchanged support signatures and quality (`:36–46,104–105`). Its memo means “computed”; the queue treats completion as “delivered.”

Concrete trigger: a full preview for A and B is running, then a new settled request changes only B before the first reply. The first A+B reply is discarded. The same worker skips A in the second request and returns only B. A's initial preview never arrives; if A previously changed from another signature, its old surface can fade out without receiving the missing replacement. The next equal document/fingerprint is also deduplicated. This affects view correctness, not accepted geometry or Undo.

A bounded Node 24.15.0 probe executed the actual queue class with supplied signatures and a fake Worker, simulating those replies. It observed one retained worker, two requests, no delivered first result, and only B delivered from the second result. The worker's skipping behavior is source observation, not execution of its WASM/browser geometry path. Two initial probe harness failures were resolved by using Node's TypeScript transform and giving the inline module a valid worker URL base; no repository files changed. Confidence: high in the mismatch, medium in its ordinary UI frequency.

Smallest correction: deliver signature-valid per-instance results from a superseded geometry request, retaining the existing source/clear cancellation boundary. Alternatively reset worker memoization when discarding its output. The existing `PreviewOverlaySurfaces.replace` already receives request and current signatures (`src/decorators/preview-overlay-surfaces.ts:50–85`), so a narrow per-instance delivery policy fits the current design. Do not add document revisions or durable acknowledgements. Acceptance should force two independent decorations, delay the first preview, change only one group, and assert both latest surfaces remain. Include accepted→live→settled transitions, source disable/replacement, cancellation, and Chromium/WebKit. Existing adaptive-worker assertions (`tests/decorator-adaptive-browser.mjs:120–125`) cover skip behavior, but their serial worker requests do not cover this queue race.

## 2. P2: Body styling invalidates all body GPU geometry

`bodyView.update` combines body-array identity with hover, face/edge/body selection, visibility and workspace into one key (`src/model/body-view.ts:57–83`). Every key change clears and disposes the entire group, then builds all visible faces and edges (`:84–104,114–119`). `faceGeometry` welds vertices and recomputes normals (`:26–36`); even hovering a different face therefore repeats geometry processing and GPU allocation for unchanged bodies. Selecting a body or entering/leaving a workspace has the same lifetime effect. This is an observed allocation path; no frame-time or model-size claim is supported by this review.

Preserve each face/edge drawable while its source object remains identical. Update face color, stencil ownership, visibility and selected edge overlays separately. Rebuild only changed body's geometry and dispose removed resources. Object identity is sufficient inside this view: retained bodies already have stable identity, and geometry candidates replace objects. Stable IDs remain lookup keys, not proof that geometry is unchanged. The current section-stencil update already changes materials without retessellation (`:60–64`), demonstrating the local boundary to extend. Keep source-edge highlights for a finish candidate (`:156–160`).

Counterevidence: camera changes alone normally hit the early return; cleanup correctly disposes resources. This is not an unconditional per-frame rebuild or a demonstrated leak. Acceptance should instrument face-geometry creation/disposal during hover and selection, assert zero unchanged face rebuilds, then exercise offset/fillet previews, acceptance, cancellation, Undo, visibility and complementary sketch clipping. Compare screenshots and GPU resource counts over repeated cycles. Confidence: high.

The sketch path has the same concern at smaller granularity. `drawSketches` resamples every visible curve and replaces line geometry when its selection/hover key changes (`src/sketch/drawing.ts:40–63,87–130`), including both visible and obscured passes. However, point highlighting deliberately changes segment subdivision (`src/sketch/point-colors.ts:30–38`). A blanket “colors only” optimization would change current point gradients. First distinguish curve sampling from feedback sampling; optimize only after a representative probe.

## 3. P2: Two edge candidate pipelines duplicate geometry work and policy

Ordinary modeling uses `pickModels`, which first calls `pickFace` and then `pickBodyEdge` (`src/sketch/model-selection.ts:156–168`). The latter projects every feature-edge segment, checks local face orientation, and calls `pickFace` again for each nearby qualifying segment (`src/model/edge-selection.ts:18–39`). `pickFace` scans all triangles of all visible display bodies (`src/model/body-view.ts:15–23`; `src/model/body-ray-hits.ts:30–45`). Thus a hover near a finely sampled edge can repeat full-scene triangle scans inside its segment loop. `localFaceFacing` also scans adjacent face triangles for its nearest normal (`src/model/body-ray-hits.ts:58–75`). These synchronous calls precede the paint.

The overlap chooser separately implements screen-edge projection, tolerance and ranking in `edgeRayHits` (`src/model/body-ray-hits.ts:78–116`; caller `src/model/overlap-candidates.ts:24–35`). It intentionally retains deeper candidates while ordinary picking rejects covered edges. That difference must survive refactoring; replacing ordinary picks with unfiltered overlap hits would change selection behavior. Independent implementations also differ in whether orientation is evaluated per segment or only after choosing the best segment, making future fixes easy to apply inconsistently.

Smallest refactor: one display-edge candidate calculation with explicit visible-only versus all-depth filtering. Compute a bounded hit snapshot for the current pointer/view/display inputs and reuse face results where the probe point is the same. Prefer body/face bounds rejection before considering a general acceleration structure. Do not introduce an exact-kernel query on every hover or persist triangle indexes as identities. Acceptance: covered rear edge, curved edge beside a silhouette, multiple overlapping bodies, clipping, selected-sketch precedence, long-press chooser hover/activation consistency. Measure triangle tests and latency on representative bodies before claiming improvement. Confidence: high in duplicate work; medium in behavioral divergence without a constructed geometry case.

## 4. P3: Preview invalidation pays whole-support serialization on the UI thread

Built-in signatures stringify owning-body faces for each instance (`src/decorators/preview-signatures.ts:18–32`); a body with several decorations serializes the same vertex arrays repeatedly. Custom signatures stringify the entire document and enabled source list (`:13–15`), including BRep strings and unrelated geometry. The custom full-document dependency is an explicit contract, so narrowing its semantic input would be incorrect. `decoratorOverlay.update` runs signature creation from `World.changed` before the scene paint (`src/decorators/preview.ts:35–51`; `src/sketch/world.ts:119–120`). `PreviewQueue.pump` then structured-clones the whole document and signatures to the worker (`src/decorators/preview-queue.ts:108–113`). Worker execution therefore does not remove all preview preparation cost from the main thread.

Use view-local memoization of immutable support bodies and the shared custom document string, then serialize each changed input once. Built-ins need owning-body context including neighboring faces, not only selected triangles. Consider a scoped built-in worker payload only if measurement shows cloning is material; custom hooks must retain the documented full context. No public revision mechanism or general scene cache is warranted. Acceptance should retain the existing unaffected-group preview test (`tests/ui-decorator-membership.mjs:155`), compare same-settings/same-geometry signatures, and separately measure main-thread signature/clone cost from worker generation. Confidence: high in repeated serialization, unmeasured impact.

## Preserved boundaries and review limits

The geometry/presentation separation is substantially sound. `Body` identifies BRep as authoritative (`src/model/body.ts:33–41`); `SketchEditor.display` selects a temporary interaction candidate or accepted data (`src/sketch/editor.ts:85–87,115–116`). Rigid preview placement explicitly leaves exact transformation to acceptance (`src/model/body-placement.ts:28–91`). Its `Body` return type can still carry stale BRep and unrelated derived descriptors, so keep it behind display-only entry points; no present route to accepted export was found. Export blocks active interactions and requests accepted geometry (`src/model/export-controls.ts:11,24–34`), refines decorated tessellation on a copy with topology checks (`src/backend/export-geometry.ts:6–52`), and computes modifiers from original document context in a worker. The sequential Manifold accumulator is expected mesh application, not hooks receiving previous decorator output (`src/decorators/mesh-runtime.ts:81–129`).

Analytic sketch arrangements and profile containment exclude camera/display tessellation (`src/sketch/regions.ts:53–89`; `src/sketch/profiles.ts:15–87`). Display triangulation belongs in region/highlight/section views. Accepted-body cross sections use exact queries, stale-key guards and explicit disposal (`src/model/section-controls.ts:59–117,225–230`), while hover updates their material in place (`:145–151`). Its immutable-object profile cache is a useful local pattern.

`continuation.ts` imports the immediate-correspondence WeakMap from `backend/kernel-result.ts`; that module is host-free, not Electron leakage. Moving correspondence into a shared model module could clarify direction during an ownership refactor, but changing this alone has little product value. Browser workers, DOM and Three.js are appropriately presentation concerns; this trace found no host API imported through the reviewed shared rendering paths.

Rendering is demand-driven, with coalesced `requestDraw`, explicit animation cancellation and worker/resource disposal. However `editor.refresh` still draws synchronously (`src/sketch/editor.ts:146–150`), and each paint invokes the broad changed set. Decorator compositing performs a scene occlusion pass per visible surface (`src/decorators/preview-compositor.ts:90–94,118–133`), repeated for the sketch foreground. This is necessary current occlusion policy, not evidence for a new renderer framework; probe before optimizing. Both render passes restore renderer state in `finally`. Actual WebKit shader, stencil and multisample acceptance remains unverified here.

Size warnings: `src/sketch/editor.ts` is 303 lines. Functions exceeding 80 lines include the preview worker handler (`src/decorators/preview-worker.ts:78–176`) and `modelHighlight` (`src/sketch/model-highlight.ts:9–94`). The handler's runtime dispatch and per-instance cache/delivery are coherent extraction seams; the highlight installer mixes triangulation with lifecycle. Do not mechanically split the 286-line World or add forwarding modules to satisfy counts. Prioritize preview correctness, then body drawable lifetime, then measured picking/signature work.
