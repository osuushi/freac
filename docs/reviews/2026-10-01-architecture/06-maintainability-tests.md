## Composition worth preserving

The project has practical composition roots. `src/sketch/main.ts:79` creates one World and SketchEditor, then wires concrete controls and explicit callbacks (`:122–161`); its pagehide block owns disposal (`:204`). Electron and the development backend instantiate the same application owner rather than alternative model implementations. `src/backend/dev-plugin.ts:9` supplies localhost development transport and closes its owner with the server. Avoid replacing this with packages, service locators, a generic dependency-injection container or a universal tool engine. Visible registration order currently affects pointer routing; moving initialization is a behavioral change, not merely tidying imports.

Likewise folder crossings do not identify broken layers. `model` includes presentation, selection and operation inputs; `sketch` includes shared geometric types and editor code. Type-only dependencies on `SketchEditor` in `body-view.ts:7`, `body-ray-hits.ts:2` and `edge-selection.ts:2` do not make a runtime editor cycle. The primary's corrected approximate import scan finds a 14-module geometry component and six-module selection component; I verified the edges below directly. Dynamic imports/reexports are outside that scan, and component size is not evidence of a runtime failure.

Tests provide substantial useful evidence. `tests/preview-cancellation.test.ts:11` uses DocumentOwner and real native geometry to check cancellation, unchanged accepted identity, volume and Undo, closing the owner in finally. `tests/body-offset-decimal-contact.test.ts:9` opens a captured exact model and independently checks requested travel against a known 9.78 mm gap. `tests/ui-extrude-preview.mjs:17` delays delivery after a real native calculation rather than substituting geometry. `tests/native-documents.mjs:9` owns isolated Electron profiles, while ordinary routes use real buttons/keyboard and read-only inspection. Preserve those routes and fixture provenance; a dependency cleanup should not substitute helper-only acceptance.

## Prioritized findings

### P2 — Runtime selection can silently turn a verification command into no coverage

`tests/scale-ui.mjs:34–45` skips browser engines unless `FREAC_TEST_BROWSER` matches and only enters Electron for the exact value `electron`. A misspelled value runs no routes and reaches normal completion. `tests/transform-followup-ui.mjs:8–9` does the same for any unsupported value, including `electron`; this runner supports browsers only. In contrast, `tests/ui.mjs:102–105` rejects unsupported runtime names. This is a concrete static control-flow defect in test invocation, not a claim that a supported runtime currently fails.

The smallest coherent repair is a shared selector that validates against each runner's declared supported engines, rejects an empty selected set and reports executed route/runtime names. Reuse a small owned launcher for the repeated Vite/browser/hidden-Electron setup, cleanup and error collection in two focused suites first. Keep the existing route functions and special host/document-dialog handling explicit; do not create a broad test framework.

Acceptance should deliberately request a typo and unsupported Electron mode and require nonzero exit before starting a server, then run one supported route per runtime and verify cleanup after a thrown route. Add a narrow failure-path check for these harness semantics. **Confidence:** high from source; not executed here. **Counterevidence:** the main browser runner already validates, and the focused launchers generally use finally cleanup. Centralizing selection should preserve those strengths.

### P2 — Source-built and externally supplied OCCT SDKs are not established as behaviorally equivalent

`scripts/setup-kernel.mjs:18–19` uses `OCCT_ROOT` directly when supplied. Without it, setup verifies a pinned source archive (`:20–34`) and applies Freac's rounded-offset precision adaptation (`:44–59`) before building. The installed-SDK path skips that adaptation. `native/kernel/CMakeLists.txt:5` checks exact OCCT 7.9.3 version, which does not distinguish adapted and stock libraries. `docs/development.md:35` advertises the installed-SDK alternative; its existing verification claim at `:43` does not specify that distinction. Therefore a stock SDK can select different native implementation despite the same version string. This is a reproducibility/precision risk, not a reproduced kernel failure.

Resolve the intended supported SDK contract first: record/check adaptation provenance where matching behavior is required, or explicitly document the stock-SDK limitation and verify its supported behavior. Keep the current source build available and avoid an agent-owned SDK prerequisite. Test the same rounded-offset/shell precision fixtures against independently built adapted and stock SDKs; include import/open and subsequent edits, not version checks alone. **Confidence:** high on the conditional source path, medium on consequences. **Counterevidence:** the Codex worktree setup (`.codex/environments/environment.toml:27–39`) checks setup source compatibility and architecture before sharing the main installed SDK, and the clean source route is pinned. That optimized workspace route does not establish arbitrary external-SDK equivalence.

### P2 — Separate foundational data utilities from validation/edit dependencies

`src/sketch/document.ts:1–7` combines schema with runtime validation imports, `newId` (`:115`), emptySketch and withSketch, and `validateSketch` (`:142`). `geometry.ts:2` needs newId from document; document imports `constraint-geometry`, which imports geometry (`constraint-geometry.ts:3`). `point-links.ts:2–4` and `point-incidence.ts:2–5` combine validation with ID allocation and editing helpers. A caller that only constructs a line or allocates an ID thereby loads the validation/editing graph. Separately, geometry imports `constraintCurves` (`geometry.ts:1`) while constraint geometry imports distance. These verified cycles are consequences of mixed responsibilities, not inherent solver complexity.

Keep the data types and simple document assembly stable; move validateSketch/validateCurve into an explicit validation entry point that imports those types only. Separate elementary point arithmetic from sketch creation/selection edits so numeric constraints do not depend on the creation module for distance. ID generation can stay with foundational assembly if that module no longer imports validation. Migrate actual import consumers coherently; do not scatter forwarding exports just to make the graph look acyclic. Splitting every tangency file is unnecessary.

Acceptance should retain native/backend and archive validation checks, invalid-reference/duplicate-ID rejection, constraints, creation attachment, Undo and actual point movement. Verify browser and host builds because the boundary serves both. **Confidence:** high on dependency direction, medium on refactor payoff; no initialization exception was observed. **Counterevidence:** the helpers use functions rather than eager cross-module reads and current typechecks/tests provide substantial safety. The priority is lowering change coupling, not fixing an alleged existing model-owner defect.

### P3 — Point enumeration belongs below picking; preserve target semantics

`selectionFrame` (`src/sketch/selection-frame.ts:9`) needs selected-point coordinates via `selectedPointHits` (`point-selection.ts:111`). That calls `pointHits` exported by `picking.ts:176`; picking itself imports selectionFrame and transformHandles (`:10–11`). The transform path continues through `transform-handles.ts:2` to `clearTransformArrow`, `scaleSelection`, then selectionFrame (`scale-selection.ts:3`). Bounds/selection calculations consequently depend on viewport picking imports although they do not perform a hit test.

Extract typed point enumeration, point identity and coordinate resolution into one geometry/selection module consumed by both picking and point selection. Retain actual hit precedence, screen tolerances and widget availability in picking. Then consider separating `ModelSelection`'s ordered state/operation resolution from viewport `pickModels` in `model-selection.ts:130`, which currently imports body rendering to obtain pickFace (`:2`). This is a bounded seam, not a demand to rename all folders.

Acceptance must preserve coincident default targets, explicit chooser narrowing, group handles, point/whole-curve separation, ordered pair application, rotated rectangles and Transform bounds. Existing selection-target, point-selection, typed-selection UI and widget routes are suitable. **Confidence:** high on runtime cycle and responsibility mixing; no regression inferred from the cycle alone. **Counterevidence:** selectionFrame also legitimately computes screen-sized handle placement; that presentation calculation should remain a view helper rather than being advertised as entirely pure geometry.

### P3 — Make supported verification coverage visible at the command boundary

`package.json:18–24` exposes unit, main browser and built Electron suites, but current tools also have focused entry points such as `scale-ui.mjs`, `transform-followup-ui.mjs` and `focus-loss-ui.mjs` outside the main `tests/ui.mjs`/`electron.mjs` route lists. Their duplication already produces differing engine support and defaults. The only checked-in CI workflow is a manual, main-only macOS release (`.github/workflows/release-macos.yml:2–14`). Its check/package step (`:117`) runs typecheck, Biome, unit and release checks, then packaging/host smoke; it does not run the ordinary browser tool routes. Thus a successful general command or release workflow cannot establish all current interaction contracts.

Maintain one small route inventory with supported runtimes and built/dev prerequisites, and use it to compose an explicitly named current-tool smoke command. Keep slower geometric suites independently selectable. Add a bounded supported-macOS verification gate using pinned setup and the current short smoke routes; this does not justify pretending Linux/Windows already work or launching the entire long UI suite on every edit. **Confidence:** high on checked-in invocation coverage, unknown on external/manual CI runs. **Counterevidence:** docs/development.md already documents many focused commands and the release workflow checks packaged source/licensing and real Finder-style host launch. Consolidate discovery, not those distinct purposes.
