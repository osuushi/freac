# Geometry and native calculator review

Baseline: `59bc72668a33fba550c7d8ba14b8bb3ab28abe2a`. This is a source and contract review, not a geometry certification. I read the architecture/process entry points, local brief, solids, topology editing, solver, cleanup and model contracts, and the relevant kernel/topology reference chapter. No tests, native builds, UI acceptance or performance measurements ran in this lane. Existing tests cited below were inspected, not executed. Dated reference experiments are counterevidence and context, not current requirements.

## Ownership and representative paths

The important architectural choices are implemented consistently. `Body` stores a materialized BRep alongside derived presentation (`src/model/body.ts:37`, `Body`), and neither calculator stores an accepted application document. Kernel `main` reconstructs `operands` inside each request (`native/kernel/main.cpp:122–164`); solver `main` creates a fresh `Calculation` with disposable coordinates, constants and `GCS::System` (`native/solver/main.cpp:16–45, 188–198`). Persistent C++ processes are calculation workers, not native document owners. TypeScript retains candidates and accepts snapshots; cancellation detaches the child before reusing its slot (`src/backend/native-calculator.ts:78–99`). The separate serialized query worker is also a reasonable boundary (`src/backend/geometry-queries.ts:9–44`): a section query cannot mutate the accepted edit candidate.

Representative modification: Face Offset starts from the accepted document in `DocumentOwner.dispatch` (`src/backend/document-owner.ts:231–243`), calls `SolidEdits.calculate` and `FaceOffsetEdit.calculate` (`src/backend/solid-edits.ts:128–132`; `src/backend/face-offset-edit.ts:15–49`), then sends current BReps and selected IDs. Native `operands` verifies the serialized topology envelope and associates IDs with current OCCT entities (`native/kernel/main.cpp:92–118`). `offsetFaces` expands tangent chains, prepares private geometry, constructs and validates the offset, and records modified/generated correspondences (`native/kernel/face-offset.cpp:42–87, 90–150`). Presentation emits predecessor IDs and temporary face/edge indexes (`native/kernel/presentation.cpp:29–33, 178–190`). `materialize` retains an ID only for a unique one-to-one continuation; retained originals, copies, splits and merges get distinct identities (`src/backend/kernel-result.ts:36–60`). It resolves indexes to stable IDs, and Offset converts native selection flags back to those IDs. Acceptance occurs separately, through `DocumentOwner.accept` and snapshot history (`src/backend/document-owner.ts:147–160`; `src/backend/document-store.ts:65–86`). `ModelSelection.sync` retains surviving body/face/edge IDs and drops missing ones (`src/sketch/model-selection.ts:68–102`). This is a complete correspondence path, without feature replay.

Exact versus display boundary: native presentation meshes the exact result, derives bounds and analytic support descriptions, and serializes the BRep without triangulation (`native/kernel/presentation.cpp:159–195`; `native/kernel/main.cpp:80–85`). Picking returns stable face IDs from presentation triangles (`src/model/body-ray-hits.ts:18–46`); projection instead reads spatial curves from the BRep and explicitly bounds cubic conversion (`native/kernel/projection.cpp:77–127, 137–147`). Save strips meshes and stores only BRep plus the topology envelope; Open inspects and regenerates presentation (`src/model/document-archive.ts:4–18`; `src/backend/open-document.ts:32–35`). Source tests cover transform/copy identity and reopening (`tests/body-transform.test.ts:9`), split Booleans (`tests/body-boolean.test.ts:127`), offset merges (`tests/body-offset-contact.test.ts:50`), cleanup scope (`tests/body-cleanup.test.ts:59, 102`) and analytic/bounded projection (`tests/projection.test.ts:16`). Those are substantial strengths, although their current execution results belong to the primary review.

## Prioritized findings

### P2 — The native reply contract does not describe the actual protocol

**Source fact.** `KernelResult` makes `mode`, `participants` and `results` mandatory while placing query-specific outputs in optional fields (`src/backend/kernel-result.ts:5–24`). Native topology, measurement, sections, projection and edge-selection branches return their own shapes without that mandatory geometry envelope (`native/kernel/main.cpp:135–159`). Inspect returns `mode: "inspect"`, outside TypeScript's `BooleanMode` (`native/kernel/geometry.cpp:89–92`). `NativeCalculator.start` only parses JSON and casts it to the requested output (`src/backend/native-calculator.ts:28–33`). Materialization checks derived indexes, but does not validate predecessor domains or finite body/presentation fields; ordinary acceptance validates sketches, not body envelopes (`src/backend/document-store.ts:69`).

**Risk/inference.** A response-format mistake or stale executable can pass the apparent type boundary and become a malformed candidate or an unrelated downstream exception. This is not evidence of current native corruption: current producers are controlled, OCCT validates shapes, and solver replies receive independent length/finite/residual checks (`src/backend/solver-residuals.ts:111–118`).

**Minimal refactor.** Define small request-specific reply types and narrow methods for operation, inspect, projection, sections, measurement and topology. Validate their structural and numeric invariants once at the adapter, keeping geometric feasibility in C++. For mutation replies, validate participants/predecessor kinds against supplied input identities before allocating IDs. Keep archive inspection distinct because its supplied identity envelope is the source. No schema generator or transport framework is needed.

**Acceptance.** Exercise each existing native request/reply variant, inject a malformed reply into the adapter, and prove rejected candidates leave accepted data/history unchanged. Re-run actual offset/Boolean/Undo/Open and query routes. Confidence: high on the contract mismatch; medium on practical failure frequency.

### P2 — Most solid requests serialize display geometry the kernel never consumes

**Source fact.** Sweep input already reduces bodies to `{id, brep, faces/edges: {id, signature}}` (`src/backend/kernel-input.ts:49–54`). Most other calculator inputs declare full `Body[]` (`src/backend/solid-calculator.ts:22–64`), and Offset, Shell, movement, finish, transform and cleanup pass those full bodies (`src/backend/solid-edits.ts:39–59, 80–98, 125–151`). Native `operands` reads only the reduced exact envelope. `NativeCalculator.launch` synchronously stringifies the whole input (`src/backend/native-calculator.ts:69`).

**Risk/inference.** Detailed curved bodies repeatedly encode, transmit and parse unused triangle arrays, outlines and derived control data during previews. This is a deterministic extra workload, not a measured latency finding. BRep transfer/reconstruction remains necessary under the selected stateless design.

**Minimal refactor.** Extract the existing exact-body envelope mapper/type and apply it consistently to native requests, including queries. Keep full bodies at document/presentation boundaries. Do not add a persistent native shape cache or second geometry owner.

**Acceptance.** Compare reduced and current requests for identical BRep, IDs, correspondence and query outputs; record serialized byte counts and preview timings on an existing spline/fillet fixture. Confirm cancellation and reopened editing. Confidence: high on redundancy, unmeasured on performance magnitude.

### P2 — Manual and backend sweep eligibility disagree on opposite normals

**Source fact.** `liftSelection` rejects normals whose signed dot product is below `1 - 1e-7` (`src/model/operation-selection.ts:142–160`). Backend `profileInput` uses the absolute dot product, accepting antiparallel planes (`src/backend/kernel-input.ts:34–42`). Both then use the first source's normal to establish sweep direction.

**Risk/inference.** Selecting parallel faces with opposite outward normals, or equivalent sketch planes with opposite orientation, can be unavailable through manual resolution while the same backend/script source list is accepted. The mismatch is certain from source; desired behavior is not settled by the broad “parallel planes” contract or this review.

**Minimal refactor.** Choose and document oriented-direction semantics for the existing tools, then share the geometric predicate between resolution and input validation. Preserve source order and signed sweep distance. This is a small product-contract reconciliation, not authorization to broaden sweep behavior.

**Acceptance.** Compare manual and script requests using same-normal, opposite-normal and nonparallel sources, both source orders and distance signs. Check actual resulting material. Confidence: high on divergence, unresolved on which rule should win.

### P2 — Numerical budgets have names locally, but no coherent cross-operation policy

**Source fact.** Several modules separately define a `1e-6` geometric tolerance (`native/kernel/boundary-move.h:11`, `shell-validation.h:7`, `offset-geometry.h:6`). Freeform offset distinguishes `2e-6` topology bounds from `1e-6` geometric checks (`offset-geometry.cpp:130–157`) and a `0.001` generated-vertex adjustment budget (`offset-geometry.h:7`; `offset-repair.cpp:21–33`). Projection splits its `0.001` conversion budget into two halves (`projection.cpp:112–125`). Small-volume policies differ: generic solid extraction uses `1e-12`, reconnection requires positive oriented volume above `1e-7`, and strict offset uses tolerance cubed (`booleans.cpp:53`; `boundary-validation.h:26–39`; `offset-geometry.cpp:138–140`).

**Risk/inference.** Tiny valid solids can enter via one operation and reject another; future fixes can accidentally change the wrong budget. Different units and purposes justify different thresholds, so merging every epsilon into one constant would be harmful. Likewise, the vertex adjustment allowance does not permit a `0.001` final boundary error: incident geometry still must meet at `1e-6`.

**Minimal refactor.** Document current units and roles, then name shared construction, boundary-distance, topology, conversion and degeneracy policies where meanings actually match. Keep operation-specific conservation/orientation checks explicit. Review reconnection's volume floor with a concrete small-body case before changing it.

**Acceptance.** Use the same small/ordinary/large and translated geometries across creation, rigid transform, boundary reconnection, offset, projection and reopening. Preserve existing captured regressions and strict rejection cases. Confidence: high on duplication and differing floors, medium on affected practical scales; no universal precision guarantee follows.

## Smaller extraction opportunities and limits

`geometry.cpp::wire` duplicates line/circle/arc/cubic construction already in `sketch-curve.cpp::sketchCurve` (`geometry.cpp:22–48`; `sketch-curve.cpp:10–21`). Their unknown-kind handling and arc failure reporting differ. Reuse one typed curve decoder and retain wire/face construction checks at their caller; verify mixed analytic/cubic sweeps and projection. This is P3 maintenance work.

Size warnings: no reviewed production native source exceeds 300 lines, but `geometry.cpp::calculate` is 98 lines, `kernel-result.ts::materialize` is 88, `solver-input.ts::solverInput` is 97, and `native/solver/main.cpp::Calculation::add` is 82. Each crosses 80 with real mixed duties. Split sweep participant selection from operation dispatch, ID planning from face-reference conversion, solver relation assembly from target preparation, and constraint-family decoding from dispatch. Preserve contiguous responsibilities; avoid forwarding-only files. `DocumentOwner.dispatch` also crosses 80 and belongs to the ownership lane.

Ephemeral correspondence is correctly nonserialized, but shared decorator continuation imports its WeakMap from the backend (`src/decorators/continuation.ts:1`). If adapter contracts are extracted, keep correspondence in a host-free geometry module: renderer preview continuation already uses it. `placedBodies` deliberately returns a `Body` with transformed presentation and old BRep/signatures (`src/model/body-placement.ts:28–89`); make that display-only distinction clearer at its narrow consumer boundary rather than treating it as accepted geometry.

Finally, signatures are type/orientation/mass/centroid summaries (`native/kernel/presentation.cpp:151–157`), not collision-free geometric identity. They supplement ordered BRep topology on restore and seed operation cleanup (`src/model/cleanup.ts:73–93`); they should not become general correspondence matchers. Current operation history and explicit reconnection bijections are stronger. Arbitrary topology histories, degenerate edges, all scale cases, platform packaging and numerical completeness remain unverified here. The useful next work is tightening these existing seams, not replacing the materialized document model.
